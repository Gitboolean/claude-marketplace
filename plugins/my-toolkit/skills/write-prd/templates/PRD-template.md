## 5. Критерії приймання

<!-- Інструкція для скіла: щонайменше один AC КОЖНОГО з 5 типів покриття (основний сценарій / помилка / авторизація / доменний інваріант / міжконтекстний), без верхньої межі. Скіл пропонує стільки, скільки потрібно, щоб кожну US покривав щонайменше один AC. Формат (Дано/Коли/Тоді = Given/When/Then):

### AC-NN (US-XX) — <тип покриття>
**Дано** <бізнесові передумови: роль актора, стан його доменних об'єктів, попередні події>
**Коли** <бізнесова дія з точки зору актора>
**Тоді** <спостережуваний бізнес-результат: актор бачить X / система блокує Y і пояснює Z / система фіксує W>

AC = спостережуваний бізнес-результат з точки зору актора. НЕ те, як система це робить.

ЗАБОРОНЕНО в тексті AC (нульова толерантність — критик F6 + regex перед записом):
- HTTP-методи (GET/POST/PUT/PATCH/DELETE)
- URL-шляхи (/courses, /lessons/{id}, /api/v1/...)
- числові коди статусу в тексті (200/201/400/401/403/404/409/5xx)
- рядки кодів помилок за шаблоном `[a-z_]+\.[a-z_]+` (напр. order.not_owner)
- JSON-фрагменти / тіла запитів ({field: "value"})
- SQL / конструкції БД (UNIQUE, FK, сирі INSERT/SELECT/UPDATE, назви обмежень, типи помилок драйверів / ORM)
Технічне відображення цього живе в `api-forge` + `decide-adr`. Тут — лише те, що бачить актор.

Дозволено: ролі з глосарію, НАЗВИ доменних інваріантів як фрази природною мовою («немає опублікованих уроків», «унікальний порядковий номер у межах курсу»), доменні об'єкти з глосарію.

5 обов'язкових типів покриття (щонайменше по 1):
1. основний сценарій — актор проходить головний потік → система фіксує результат і підтверджує.
2. помилка — актор надсилає некоректні дані → система блокує і простими словами пояснює причину.
3. авторизація — в актора немає прав → система відмовляє в доступі АБО приховує існування (обґрунтування в бізнес-термінах).
4. доменний інваріант — актор порушує названий інваріант → система блокує і простими словами називає інваріант.
5. міжконтекстний — дія актора залежить від стану в іншому bounded context → система застосовує міжконтекстне правило.

Познач кожен AC його US-NN. Граничний випадок паралельних дій → додай як AC-NNb, теж бізнес-мовою. -->

### AC-01 (US-01) — основний сценарій

**Дано** авторизований <роль> володіє чернеткою <доменний-об'єкт>
**Коли** <роль> намагається опублікувати <доменний-об'єкт>
**Тоді** система фіксує <доменний-об'єкт> як опублікований і підтверджує це <роль>

### AC-02 (US-01) — порушення доменного інваріанта

**Дано** авторизований <роль> володіє чернеткою <доменний-об'єкт> без жодного вкладеного <під-об'єкт>
**Коли** <роль> намагається опублікувати <доменний-об'єкт>
**Тоді** система блокує публікацію і повідомляє <роль>, що спершу треба опублікувати щонайменше один <під-об'єкт>
