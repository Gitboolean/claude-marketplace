## Антипатерни (повний перелік)

На додачу до антипатернів у SKILL.md:

- **Пропуск вхідного інтерв'ю** — ідею треба зафіксувати в 1–3 реченнях дослівно через `AskUserQuestion` до початку чернетки. Реконструкція ідеї з припущень моделі — помилка коректності, а не компроміс заради швидкості.
- **Назви конкретних технологій у §1–§3** — конкретне сховище, брокер, фреймворк чи бібліотека. PRD — це ЩО + НАВІЩО; ЯК живе в `architecture-design`.
- **Деталі реалізації в AC** — HTTP-методи / URL-шляхи / числові коди статусу / рядки `module.error_name` / JSON-фрагменти / конструкції SQL у тексті AC з §5. Це відображення живе в `api-forge` (HTTP / схеми / рядки помилок) і `decide-adr` (рішення про обмеження БД).
- **Артефакти брейншторму чи ініціатив як вхід PRD.** PRD спирається лише на CONTEXT + idea-brief (обов'язкові) плюс канали, які обрав користувач.
- **Пропонувати, не прочитавши код** (коли обрано канал «Код еталонного модуля»). Увесь сенс write-prd — спиратися на справжні патерни.
- **Приймати AC без Дано/Коли/Тоді.** Формулювання «фіча працює» / «основний сценарій» провалюють DoD. Перепиши в Дано/Коли/Тоді до `AskUserQuestion`.
- **Ігнорувати інструкції в шаблоні.** Коментарі `<!-- Інструкція для скіла: ... -->` — контракт кожної секції. Без них виходить структурно правильний, але змістовно порожній PRD.
- **Одне `AskUserQuestion` «прийняти всі US».** Втрачається можливість правити кожен елемент. Секцію спершу показують батчем (7a), щоб користувач бачив загальну картину, потім — одне питання на елемент (7b).
- **«Винести у відкрите питання» без відповідального і терміну.** Скіл МУСИТЬ поставити уточнювальне `AskUserQuestion` одразу після вибору цієї опції. Якщо користувач лишив бодай одне поле порожнім — перенесення понижується до «Викинути» з явним попередженням, а не тихо потрапляє в §8 напівзаповненим.
- **Збережена US з §4 без AC у §5.** Навіть на глибині `easy` мінімум за сценаріями — це мінімум коректності. Якщо на `easy` неможливо самостійно вивести AC для збереженої US — це одне з незворотних / невивідних рішень, про яке треба запитати.
- **Запуск `general-purpose` замість `my-toolkit:critic`** без перевірки доступності. Запасний варіант — лише коли критика справді немає.
- **Пропуск кроку критика.** Сократівський цикл ловить лише проблеми окремих елементів — він не бачить розходжень між елементами, спричинених правками користувача. Записати файл без критика означає передати ці розходження далі.
- **Розв'язувати знахідки критика самостійно** (без `AskUserQuestion`). Критик виносить спірні рішення на розгляд користувача. Обрати «відкат» чи «правку» без питання — це знову тихі правки.
