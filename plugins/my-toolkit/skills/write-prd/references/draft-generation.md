# Генерація чернетки — контракт кожної секції для кроку 6 протоколу write-prd

Авторитетний формат кожної секції — коментар `<!-- Інструкція для скіла: ... -->` у [`../templates/PRD-template.md`](../templates/PRD-template.md). Цей файл — операційна зв'язка: звідки береться зміст і що заборонено.

## Вхідні дані за пріоритетом

1. **`## Глосарій` з `CONTEXT.md`** (у старих файлах — `## Glossary`) — канонічне джерело назв ролей і доменних термінів. Якщо щось йому суперечить — перемагає глосарій.
2. **`idea-brief.md`** — секції §2 «Проблема», §3 «Користувачі», §4 «Чому зараз», §5 «Поза скоупом», §11 RICE, §13 «Рекомендація».
3. **`docs/architecture-map.md`** (якщо є, від `sdlc:map-architecture`) — впливає на §1 «Контекст», обмеження в §2 і §3 «Не-цілі» (що наявна система вже вміє / структурно не може). **Не** протягуй технології з карти в §5 AC — критерії лишаються спостережуваними з боку бізнесу.
4. **Результати каналів з кроку 5** — патерни еталонного модуля (типи сутностей, маркери помилок, константи статусів, перевірки авторизації), цитати з MCP-Atlassian, документація проєкту, знахідки RAG → лише для трасування в §1 ¶4.

## Джерела для кожної секції

- **§1 Контекст** — 3–4 абзаци. ¶1 з idea-brief §2 «Проблема». ¶2 з idea-brief §4 «Чому зараз» / тригерів. ¶3 з idea-brief §13 «Рекомендація» (цитуй прямо — 1–2 речення, обраний підхід). ¶4 (опційно) патерни з еталонного модуля + цитати з MCP / документації / RAG як **контекст для трасування** — і місце, куди рішення «Залишити» на знахідки критика пишуть пункти «Свідоме рішення: <заголовок> — обґрунтування: <причина>». Ця секція — ЩО + НАВІЩО, а не ЯК. НЕ називай тут конкретне сховище / брокер / фреймворк / бібліотеку — це належить `architecture-design`.
- **§2 Цілі** — 2–3 вимірювані стратегічні результати списком. Кожен — прояв обраного підходу (§1 ¶3). Тут без сирих чисел — числа живуть у §7 KPI.
- **§3 Не-цілі** — 3–4 явні не-цілі, кожна — одне речення + причина. Джерело: idea-brief §5 «Поза скоупом». Тримає скоуп чесним.
- **§4 User stories** — ≥5 US (без верхньої межі) у формі `Як <роль> / Я хочу / Щоб`. Скіл пропонує стільки, скільки потрібно, щоб покрити всі ролі з глосарію CONTEXT + усі цілі з §2. Ролі — **лише** з глосарію CONTEXT (жодних вигаданих `user`/`admin`, якщо глосарій визначає конкретні ролі).
- **§5 Критерії приймання** — див. контракт §5 AC нижче.
- **§6 Таблиця NFR** — рядки з рекомендованого переліку з числовими цілями. Жодних «швидко» / «надійно» / «високий». Вимірювання = назва конкретної метрики з продакшену. TBD допустимо лише з відповідальним і терміном, прив'язаними до рядка в §8.
- **§6.1 Безпека / приватність** — класифікація даних, які персональні дані зачіпаємо, вплив на authZ/authN (без прив'язки до інтерфейсу — жодних ендпоінтів / маршрутів; інтерфейси виводить `architecture-design`), **3–5 сценаріїв зловживань** (доступ до чужого tenant, витік чернеток, ін'єкції через URL / текстові поля, масове створення зі спамом при rate limit, опційно — зловживання токеном; для кожного — бізнес-реакція), висновок security review.
- **§7 Метрики / KPI** — ≥3 метрики (без верхньої межі), зараз → ціль із часовими рамками. Зараз=0 — нормально для нової фічі; зараз=TBD вимагає плану вимірювання прямо тут.
- **§8 Відкриті питання** — 2–4 записи, кожен з відповідальним і терміном (дата або тригер етапу). Формат: `- [ ] <питання>? Поки що за замовчуванням: <X>. — відповідальний: <ім'я/роль>, до: <дата або етап>`.

## Контракт критеріїв приймання §5

AC описує **спостережуваний бізнес-результат з точки зору актора** у формі Дано/Коли/Тоді (Given/When/Then). **Без верхньої межі** — пропонуй стільки, скільки потрібно, щоб **кожна user story з §4 мала щонайменше один AC** і були всі п'ять типів покриття. Якщо під час сократівського проходу «Викинути» / «Винести у відкрите питання» лишає порожнім тип покриття **або збережену user story з §4 без AC** — перегенеруй заміну і проведи по ній міні-батч (два мінімуми покриття — див. [`socratic-loop.md`](./socratic-loop.md)). Правило «кожна US має щонайменше один AC» — **мінімум, який перевіряється повторно**, а не лише ціль чернетки: він перевіряється після кожного рішення в §5, щоб наступні `complete-sequence-diagrams` і `review-feature` могли покластися на те, що в кожного сценарію є перевірюваний критерій.

П'ять типів покриття, щонайменше по одному:

1. **основний сценарій** — актор проходить головний потік → система фіксує результат і підтверджує.
2. **помилка** — актор надсилає некоректні дані → система блокує і пояснює причину (формулюй як «система показує актору, що <поле> має бути <обмеження>»; без HTTP-коду, без рядка коду помилки).
3. **авторизація** — в актора немає прав (чужий tenant / інша роль / не власник) → система відмовляє в доступі або приховує існування; обґрунтування в бізнес-термінах (без `403`/`404`).
4. **доменний інваріант** — актор порушує названий інваріант → система блокує дію і простими словами називає інваріант (без рядка коду помилки, без `409`).
5. **міжконтекстний** — дія актора залежить від стану в іншому bounded context → система застосовує міжконтекстне правило.

## Заборонені токени в §5 AC (незалежно від стеку, нульова толерантність)

Перевіряє F6 критика і regex-сканування перед записом:

- **HTTP-методи**: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`.
- **URL-шляхи**: усе, що починається з `/` і далі ідентифікатор у нижньому регістрі (`/orders`, `/items/{id}`, `/api/v1/...`).
- **числові коди статусу** в тексті AC: `200`, `201`, `400`, `401`, `403`, `404`, `409`, `5xx`, `500`, `503`.
- **рядки кодів помилок** за шаблоном `[a-z_]+\.[a-z_]+` (напр. `order.not_owner`, `validation.title_too_long`).
- **JSON-фрагменти / тіла запитів**: `{title, description}`, `{id, status: "draft"}`.
- **SQL / конструкції БД**: `UNIQUE(...)`, `FK`, сирі `INSERT`/`SELECT`/`UPDATE`, назви обмежень — і будь-які **типи помилок конкретного драйвера / ORM** (напр. `pq.*`, `sqlalchemy.*`).

Технічне відображення всього цього живе в `api-forge` (HTTP-метод / шлях / статус, рядки кодів помилок, схеми запитів) і `generate-data-model` / `decide-adr` (конструкції БД). AC у PRD — це те, ЩО може спостерігати користувач, а не ЯК система це кодує.

## Гігієна §1–§3 незалежно від стеку

Продуктові секції не мають називати **конкретну технологію** — конкретне сховище, брокер повідомлень, фреймворк чи бібліотеку. Познач будь-яку власну назву продукту / бібліотеки в секціях ЩО/НАВІЩО і перенеси її на етап `architecture-design`.

## Гігієна перед записом (до сократівського проходу)

- Кожна не-ціль у §3 має причину (нічого не вигадуємо).
- §1 ¶3 цитує idea-brief §13 «Рекомендація» дослівно або переказує, не втрачаючи напряму.
- **У §5 є щонайменше по одному AC кожного типу покриття, щонайменше один AC на кожну US з §4 і 0 заборонених токенів** (самоперевірка; критик і regex — страховка).
