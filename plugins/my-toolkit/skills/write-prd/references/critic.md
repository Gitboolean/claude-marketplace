# write-prd — відмінності від спільного критика

Прочитай [`../../_shared/critic.md`](../../_shared/critic.md): там канонічний запуск і каркас F1–F6. write-prd додає лише відмінності нижче; скіл заповнює плейсхолдери і запускає одного `Agent` у чистому контексті через `subagent_type: "my-toolkit:critic"`.

## Плейсхолдери

- **`{{ARTIFACT_NAME}}`** = "Product Requirements Document (PRD) — контекст / цілі / user stories / критерії приймання / NFR / KPI".
- **`{{DRAFT}}`** = чернетка `PRD.md` у пам'яті (повний текст, після сократівського проходу).
- **`{{EDITS_LOG}}`** = журнал правок з кроку 7 (кожен запис `edit | drop | add | save_as_oq`; прийнятих немає — вони база).
- **`{{UPSTREAM_FILES}}`** (критик читає їх сам):
  - `docs/features/<slug>/CONTEXT.md` — канонічний глосарій (ролі, доменні терміни).
  - `docs/features/<slug>/idea-brief.md` — §2 «Проблема», §3 «Користувачі», §5 «Поза скоупом», §11 RICE, §13 «Рекомендація».
  - Шляхи до еталонних модулів / документації, які користувач назвав на кроці 4 (лише шляхи, не вміст).

## Запуск

Один виклик `Agent`, `subagent_type: "my-toolkit:critic"`, **чистий контекст** — критик не бачив сократівської розмови. Якщо `my-toolkit:critic` під час виконання недоступний — запасний варіант `general-purpose` з тим самим промптом.

У промпт передай: повну чернетку PRD після сократівського проходу + журнал правок з кроку 7 + шляхи до попередніх файлів (не їхній вміст). Критик сам перечитує попередні файли в чистому контексті — жодного «отруєння переказом».

## Структурний мінімум F5 (для цього артефакту)

Після застосування всіх видалень і перенесень у відкриті питання:

- У §4 є ≥1 US на кожну роль з глосарію + на кожну ціль з §2.
- **Кожна збережена US з §4 має ≥1 AC у §5** (мінімум за сценаріями — збережена US без AC непомітно ламає покриття сценаріїв у `complete-sequence-diagrams` і наскрізне трасування в `review-feature`). AC, винесені у відкриті питання, сюди НЕ рахуються.
- У §5 є ≥1 AC кожного з 5 типів покриття (основний сценарій / помилка / авторизація / доменний інваріант / міжконтекстний). Винесені у відкриті питання НЕ рахуються.
- Усі рядки NFR у §6 мають числову ціль + спосіб вимірювання (жодних прикметників, жодного самотнього TBD).
- У §8 «Відкриті питання» є рядок на кожен `save_as_oq` з відповідальним і терміном (жодного самотнього «TBD»).

## Спеціалізація F6 — витік заборонених токенів (головна перевірка)

Це основна F6 для write-prd. Проскануй текст AC у §5 на заборонені токени з [`draft-generation.md`](./draft-generation.md) (HTTP-методи, URL-шляхи, числові статуси, рядки `module.error_name`, JSON-фрагменти, конструкції SQL / драйверів). **Перелічи кожне влучання**, один пункт на рядок AC:

```
- **[F6] AC-NN містить заборонені токени** — рядок: "<дослівний уривок>"; влучання: <токен1>, <токен2>; пропозиція: переписати в бізнес-формі (результат, який бачить актор) АБО перенести HTTP / помилку / схему в `api-forge` чи `decide-adr`.
```

Також познач будь-яку назву конкретної технології (сховище / брокер / фреймворк / бібліотека) у §1–§3 — вони належать `architecture-design`.

## Спеціалізація F1 — дрейф підходу

Якщо журнал правок викинув / змінив US чи AC, пов'язані з обраним підходом у §1 ¶3, перевір, що §1 ¶3 досі точно описує цей підхід (цитує рекомендацію з idea-brief §13). PRD, тіло якого більше не відповідає його ж абзацу «обраний підхід», — це дрейф.

## Спеціалізація F3 — відкладення vs напрям з idea-brief

Для кожного `drop` / `save_as_oq` у журналі правок перевір, чи idea-brief §5 («Поза скоупом»), §13 («Рекомендація») або §11 (RICE) називали цей елемент критичним драйвером залученості / прийняття / ризику. **Розрізняй**: «викинуто» (жорстке видалення) vs «відкладено у відкриті питання» (м'якше — елемент живий у §8 з відповідальним і терміном, його можна повернути, якщо питання розв'яжеться до наступних етапів).

## Цикл розв'язання

Кожну знахідку винось через `AskUserQuestion`:

- **«Прийняти відкат / правку, як запропоновано»** — застосувати запропоновану критиком правку дослівно.
- **«Прийняти правку (інше формулювання)»** — користувач пише своє формулювання; скіл застосовує його.
- **«Залишити (з обґрунтуванням)»** — лишити чернетку як є, користувач дає обґрунтування.

Обмеження:
- ≤2 батчі `AskUserQuestion`, до 4 питань у батчі. **Друга** відповідь користувача на знахідку — фінальна.
- **Рішення «Залишити» додає пункт** у §1 «Контекст» ¶4 чернетки: «<заголовок знахідки> — свідомо залишено автором, обґрунтування: <обґрунтування користувача>». Так свідомий вибір видно наступним скілам.

Після розв'язання знову виконай обов'язкові самоперевірки (див. `## Definition of Done` у SKILL.md). Якщо щось досі не проходить — один раз знову відкрий відповідне `AskUserQuestion`, потім продовжуй.

## Резервна regex-перевірка F6 перед записом

Незалежно від критика, перед записом файлу проскануй regex-ом текст AC у §5 на заборонені токени (HTTP-методи, шляхи, що починаються з `/`, голі коди статусу `200|201|400|401|403|404|409|500|503|5xx`, `[a-z_]+\.[a-z_]+`, JSON-фрагменти, конструкції SQL). Будь-яке влучання, яке **не** було свідомо залишене при розв'язанні знахідок критика → знову відкрий `AskUserQuestion` для цього рядка AC. Це страховка, якщо критик пропустив токен (напр. вивід обрізався).

## Збої

- **Критик не відповів / помилка** → СТОП, повідом користувача. Ніколи не записуй файл мовчки.
- **Критик повернув `CRITIC_BLOCKED: <причина>`** (не може прочитати попередні файли) → СТОП і повідом користувача. Не вгадуй.
- **Критик повернув вивід у неправильному форматі** (ні пунктів, ні `NO_CONTESTED_DECISIONS`, ні `CRITIC_BLOCKED`) → запусти ще раз, дописавши «Твій попередній вивід не відповідав потрібному формату»; якщо знову неправильно → СТОП і запитай користувача, як діяти.
- **Користувач обирає «Залишити» для кожної знахідки** → дозволено (авторство PRD — за користувачем), але кожне таке рішення додає пункт у §1 ¶4, щоб слід рішень можна було перевірити.
