# Скіл: write-prd (етап 03 — автор PRD)

Перетворює ідею на перевірений `PRD.md`: легке інтерв'ю фіксує ідею і перевіряє її на міцність, потім скіл пише чернетку продуктової специфікації (контекст → цілі → user stories → критерії приймання → NFR → KPI), сократівськи її перевіряє і перед записом запускає критика в чистому контексті. Менше друкувати, більше перевіряти. Цей файл — каркас; деталі живуть у `references/`.

Сократівський цикл, критик і стиль питань — **спільні**; цей скіл тримає лише свої відмінності:
→ [`../_shared/socratic-loop.md`](../_shared/socratic-loop.md) · [`../_shared/critic.md`](../_shared/critic.md) · [`../_shared/ask-style.md`](../_shared/ask-style.md)

Глибина керує кількістю питань і самостійністю → [`../_shared/interview-depth.md`](../_shared/interview-depth.md).

## Відповідальні

PM + Tech Lead (співавтори). PM веде цілі / не-цілі / KPI; Tech Lead — контекст і патерни, а також покриття критеріями приймання.

## Вхідні дані

**Обов'язкові** (без них скіл зупиняється):

- `<slug>` — slug фічі в kebab-case.
- `docs/features/<slug>/idea-brief.md` — проблема, RICE, рекомендація (§13), поза скоупом (§5). Немає → «спершу запусти `/my-toolkit:interview <slug>`».
- `docs/features/<slug>/CONTEXT.md` — канонічний глосарій (назви ролей, доменні терміни). Немає → «спершу запусти `/my-toolkit:fix-term <slug>`». Жодного тихого обходу.

**Опційні**:
- `docs/features/<slug>/.size` — підказка глибини (MVP чи Full за матрицею розмірів). Читається, якщо є; **якщо немає — встановлюється тут** (крок 1 класифікує і записує), щоб наступні етапи ніколи мовчки не брали M за замовчуванням.
- `--reference <шлях-до-модуля>` — передається при виклику; заздалегідь обирає канал «Код еталонного модуля» на кроці 4.

## Протокол

1. **Перевірка вхідних даних + контекст + глибина інтерв'ю.** `test -f` для обох обов'язкових файлів; якщо чогось немає — зупинись з відповідною помилкою. Далі: завантаж `## Глосарій` з `CONTEXT.md` (у старих файлах — `## Glossary`) у стан сесії (канонічні ролі й терміни). Якщо `.size` є — прочитай, щоб визначити глибину PRD; **якщо немає — встанови зараз**: класифікуй фічу за 4 сигналами з [`../_shared/size-matrix.md`](../_shared/size-matrix.md) (кількість PR / час до мержу / новий модуль·API·міграція / ламаючі зміни), підтверди одним зведеним `AskUserQuestion` (на глибині `easy` — візьми значення з матриці і запиши в журнал припущень) і запиши `docs/features/<slug>/.size`, щоб кожен наступний етап читав справжній розмір, а не мовчки брав M. Для перекласифікації при зміні скоупу лишається утиліта `sdlc:classify-size`. Якщо є `docs/architecture-map.md` (від `sdlc:map-architecture`) — прочитай, щоб PRD **знав про архітектуру**: карта впливає на §1 «Контекст», §2 обмеження і §3 «Не-цілі» (що наявна система вже робить / чого не може). Немає → запропонуй спершу запустити `/sdlc-map-architecture`, але продовжуй (PRD — продуктового рівня, його можна зафіксувати й без карти). **Не протягуй технології з карти в §5 AC** — критерії лишаються спостережуваними з боку бізнесу; карта формує обмеження, а не критерії приймання. **Потім встанови глибину інтерв'ю (перше питання):** **якщо `.claude/my-toolkit.local.md` немає — створи його** за [`../_shared/settings.md`](../_shared/settings.md) (з документованими значеннями за замовчуванням) і допиши `.gitignore`; прочитай з нього `interview_depth` (інакше — medium) і — якщо не передано аргумент `--depth=easy|medium|hard` (тоді питання пропускається) — постав ОДНЕ `AskUserQuestion` про глибину за [`../_shared/ask-style.md`](../_shared/ask-style.md), де збережене значення (або medium) — перша опція з «(Recommended)», яку можна змінити на цей запуск. Обраний рівень визначає обсяг заглиблення на кроці 2 і сократівської перевірки на кроці 7 → [`../_shared/interview-depth.md`](../_shared/interview-depth.md). (Повнота — мінімум §5 з 5 типів AC **і** мінімум «кожна user story з §4 має AC у §5» — від глибини не залежить.)

2. **Фіксація ідеї (вхідне інтерв'ю).** Одне `AskUserQuestion` для сирої ідеї в 1–3 реченнях (зберегти дослівно як точку відліку). Потім сократівське заглиблення по ясності проблеми / критеріях успіху / обмеженнях / стратегічній відповідності, батчами по 2–3 питання — обсяг залежить від регулятора глибини (easy: лише кілька питань, на які не можна відповісти самостійно, далі журнал припущень; medium: 3–5; hard: пройти кожен кут, кожен компроміс на передньому плані). Кожне питання формулюй за [`../_shared/ask-style.md`](../_shared/ask-style.md).

3. **Звіряння глосарію по ходу (жорстке правило на будь-якій глибині).** На кожен новий чи невідомий доменний термін, що з'являється в інтерв'ю або чернетці, **одразу** викликай `/my-toolkit:fix-term <slug>` — звір його з `CONTEXT.md` і додай / онови визначення, перш ніж продовжити. На момент запису PRD кожна роль з §4 і кожен доменний термін з §5 уже канонічні за глосарієм; глосарій ніколи не відкладається на потім.

4. **Запитай, які додаткові канали прочитати** (`AskUserQuestion` з multi-select): код еталонного модуля / документація проєкту / MCP-Atlassian (Confluence) / MCP-Atlassian (Jira) / база знань / нічого. Для кожного обраного каналу запитай **конкретний** шлях / запит — жодних тихих широких сканувань. Якщо передано `--reference`, заздалегідь обери «Код еталонного модуля».

5. **Прочитай обрані канали.** Еталонний модуль → витягни типи сутностей, маркери помилок, константи статусів, перевірки авторизації. MCP-Atlassian → `mcp__atlassian__search` для названих сторінок / тікетів. Документація / RAG → лише шляхи / теми, які назвав користувач.

6. **Прочитай шаблон + напиши чернетку §1–§8.** Прочитай [`./templates/PRD-template.md`](./templates/PRD-template.md) (його коментарі `<!-- Інструкція для скіла: ... -->` — контракт кожної секції). Пиши чернетку за [`./references/draft-generation.md`](./references/draft-generation.md): джерела для кожної секції, **5 типів покриття AC** (основний сценарій / помилка / авторизація / доменний інваріант / міжконтекстний) і правило **заборонених токенів, незалежне від стеку**, для критеріїв приймання. Подбай, щоб **кожна user story з §4 мала ≥1 AC у §5 вже в чернетці** (мінімум за сценаріями діє ще до початку сократівського проходу).

7. **Сократівська перевірка.** Пройди §4 US → §5 AC → §6 NFR → §7 KPI спільною машиною з 4 станів (кількість питань на рішення залежить від глибини — на easy рішення без питань ідуть у журнал припущень для пакетного вето). Відмінності write-prd → [`./references/socratic-loop.md`](./references/socratic-loop.md): у AC є 5-та опція «Додати ще один AC»; перевірка покриття §5 після видалень / перенесень у відкриті питання тримає **два мінімуми** — (a) ≥1 AC кожного з 5 типів покриття і (b) **≥1 AC на кожну збережену user story з §4** (якщо порожнім лишився тип *або* user story — перегенеруй / додай заміну). **Обидва — мінімуми, а не регулятори: діють на будь-якій глибині;** змінюється лише кількість питань. Мінімум (b) замикає зв'язок §4→§5, щоб покриття сценаріїв у `sdlc:complete-sequence-diagrams` і трасування в `sdlc:review-feature` не зламала user story, що втратила свій єдиний AC. Веди журнал правок.

8. **Критик + запис + коміт.** Запусти агента [`critic`](../../agents/critic.md) — `subagent_type: "my-toolkit:critic"` (має `model: opus` + `effort: high`, чистий ізольований контекст за [`../_shared/agent-roster.md`](../_shared/agent-roster.md)) — з відмінностями write-prd з [`./references/critic.md`](./references/critic.md) (поверх [`../_shared/critic.md`](../_shared/critic.md)): передай у промпті чернетку + журнал правок, `CONTEXT.md` і `idea-brief.md` він читає сам. Розв'яжи знахідки через `AskUserQuestion` (Прийняти відкат / Прийняти правку / Залишити з обґрунтуванням → пункт у §1 ¶4). Запусти regex-сканування заборонених токенів як страховку F6. Якщо все пройшло — запиши `docs/features/<slug>/PRD.md` (глосарій уже звірено по ходу на кроці 3) і запропонуй коміт `03: PRD for <slug>`. **Зареєструй у роадмепі:** додай / підніми фічу в **Now** у `docs/roadmap.md` (через `/sdlc-roadmap`) — одним рядком результат + посилання на теку фічі + статус; якщо вона була кандидатом у Next — підніми. (Якщо роадмепу ще немає — пропусти, він опційний.) Потім **виведи блок передачі етапу** за [`../_shared/handoff.md`](../_shared/handoff.md) — *Що я зробив* + *Перевір* (`PRD.md`, `.size`) + *Запусти далі* (`/clear`, потім `/my-toolkit:clarify-prd <slug>`). (Якщо `my-toolkit:critic` недоступний — запусти `general-purpose` агента з тими самими відмінностями.)

## Definition of Done

- `docs/features/<slug>/PRD.md` записано; усі секції заповнено (або `<!-- N/A: причина -->`).
- `docs/features/<slug>/.size` існує після цього етапу (прочитано, якщо був, інакше класифіковано і записано тут).
- У §5 після видалень / перенесень у відкриті питання є ≥1 AC кожного з 5 типів покриття, **кожна user story з §4 має ≥1 AC** (мінімум за сценаріями — жодної збереженої US без AC), і **0 заборонених токенів** (HTTP-методи / URL-шляхи / числові коди статусу / рядки `module.error_name` / JSON-фрагменти / SQL-конструкції).
- Ролі в §4 точно збігаються з глосарієм `CONTEXT.md` (жодних вигаданих `user`/`admin`).
- Кожне відкрите питання в §8 має відповідального + термін (жодного самотнього «TBD»).
- Журнал правок ведено; критик (`my-toolkit:critic`) відпрацював на чернетці після сократівського проходу; кожну знахідку розв'язано або свідомо залишено.

## Антипатерни

- **Пропуск вхідного інтерв'ю** і реконструкція ідеї з припущень моделі. Фіксація + заглиблення мусять справді ставити `AskUserQuestion`.
- **Назви конкретних технологій у §1–§3** (конкретне сховище, брокер, фреймворк чи бібліотека). PRD — це ЩО + НАВІЩО; вибір технологій належить `sdlc:architecture-design`.
- **Деталі реалізації в AC** — HTTP / статуси / коди помилок / SQL. Це відображення живе в `sdlc:api-forge` і `sdlc:decide-adr`.
- **Запуск `general-purpose` замість `my-toolkit:critic`** без перевірки доступності. Критик з простору імен плагіна має правильні model/effort і чистий контекст; запасний варіант — лише коли його справді немає.
- **Артефакти брейншторму чи ініціатив як вхід PRD.** PRD спирається лише на CONTEXT + idea-brief (обов'язкові) плюс канали, які обрав користувач.
- **Вигадані назви ролей чи доменні терміни**, яких немає в глосарії CONTEXT. Глосарій канонічний; PRD ніколи не вводить нових назв ролей.
