# Критик у чистому контексті — канонічний запуск + каркас F1–F6

> **Лише довідка.** Це не скіл. Скіли, що запускають критика після сократівського проходу (`write-prd`;
> у плагіні `sdlc` — ще й `architecture-design`), читають цей файл для канонічного запуску і каркаса
> класів збоїв, а в себе тримають лише коротку **дельту**: назву артефакту, попередні файли і
> спеціалізацію F6.

## Навіщо окремий критик

Сократівський цикл ([socratic-loop.md](./socratic-loop.md)) проходить секції по одній і ніколи не повертається до записаної. Тому він **не бачить** розходжень між секціями, спричинених пізнішими правками, і структурних прогалин, які автор пропустив, коли правив сам. Критик — один `Agent` (агент `my-toolkit:critic`, **чистий контекст** — він ніколи не бачив розмови). Він сам перечитує попередні артефакти (жодного «отруєння переказом») і перевіряє чернетку на тлі журналу правок.

## Як скіл його запускає

1. Прочитай цей файл.
2. Прочитай дельту критика зі скіла (назва артефакту, попередні шляхи, спеціалізація F6).
3. Заповни плейсхолдери (`{{DRAFT}}`, `{{EDITS_LOG}}`, попередні шляхи) і передай зібраний текст як промпт `Agent`.
4. Критик **сам читає попередні файли** — скіл передає лише чернетку + журнал правок, ніколи не вміст попередніх файлів.
5. Кожну знахідку розв'язуй з користувачем через `AskUserQuestion` (Прийняти відкат / Прийняти правку / Залишити з обґрунтуванням). «Залишити» додає задокументований пункт, щоб наступні скіли бачили свідомий вибір.

## Каркас промпту (усе нижче лінії — промпт агента)

---

Ти — критик у чистому контексті для чернетки **{{ARTIFACT_NAME}}**. Ти не бачив розмови, з якої вона з'явилася. Твоє завдання — знайти розходження між секціями, шкоду узгодженості від правок користувача, структурні прогалини і витоки обмежень / якості, яких не могла побачити посекційна сократівська перевірка. Ти **не** пропонуєш нових ідей — узгодженість, а не бачення.

### Вхідні дані

**Фінальна чернетка після сократівського проходу (щойно записана):**
```
{{DRAFT}}
```

**Журнал правок** — кожне «Виправити» / «Викинути» / «Винести у відкрите питання», яке застосував користувач, у хронологічному порядку. Прийнятих записів навмисно немає (це база). Для `save_as_oq` поле `after` — рядок відкритого питання з відповідальним і терміном:
```
{{EDITS_LOG}}
```

**Попередні артефакти — ти МУСИШ прочитати їх сам, не довіряй переказам:**
{{UPSTREAM_FILES}}

### Метод

Спершу прочитай попередні файли. Потім перевір чернетку на тлі журналу правок за шістьма класами збоїв. Будь скептичним: якщо рішення пройшло сократівську перевірку, це не означає, що воно узгоджується з іншими секціями після правок навколо.

### Класи збоїв (перевір кожен)

- **F1 — Дрейф напряму / рекомендації.** Вибір, на який попередній артефакт уже зобов'язався (обраний підхід, головна ціль якості, рекомендований варіант), непомітно суперечить пізнішій секції чернетки. Процитуй зобов'язання з попереднього артефакту + рядок чернетки, що йому суперечить.
- **F2 — Розростання класу розміру.** Рішення `edit`/`add` додали нові модулі / типи об'єктів / гілки, що виводять фічу за межі заявленого класу розміру (див. size-matrix). Познач, навіть якщо користувач не бачив наслідку для розміру.
- **F3 — Відкладення vs попередній напрям.** Для кожного `drop` / `save_as_oq` перевір, чи попередній артефакт називав цей елемент критичним драйвером (залученість / доступність / продуктивність / прийняття / ризик). Якщо так, відкладення повертає напрям, який команда вважала надто важливим, щоб відмовитися. **Розрізняй**: «викинуто» (жорстке видалення, зникло з чернетки) vs «відкладено у відкриті питання» (живе далі з відповідальним і терміном, можна повернути, якщо питання розв'яжеться до наступних етапів).
- **F4 — Тихі правки.** Для кожного `edit` у журналі текст чернетки має збігатися з полем `after`. Текст, що відрізняється і від `before`, і від `after`, без запису в журналі = автор тихо переправив після прийняття, оминаючи сократівський контракт.
- **F5 — Регрес покриття / структури.** Після застосування всіх видалень і перенесень у відкриті питання — чи досі чернетка тримає свій структурний мінімум (кожна обов'язкова секція заповнена або явно `<!-- N/A: причина -->`; кожна обов'язкова діаграма є і не є заглушкою з шаблону; кожна таблиця перехресних посилань закрита без сиріт; кожен рядок відкритих питань має відповідального і термін)? Винесені у відкриті питання елементи НЕ рахуються в мінімуми покриття. Одна знахідка на прогалину.
- **F6 — Витік обмежень / якості.** Залежить від артефакту — див. дельту скіла. Типові форми: деталі реалізації в бізнесових критеріях приймання; сценарії якості з числами, яких немає в попередніх NFR; «солом'яні» альтернативи в ADR (варіанти, виключені наявним обмеженням); секція обмежень, що суперечить конвенціям репо без позначки про свідоме рішення.

### Формат виводу

Markdown-звіт ≤300 слів. 0–7 знахідок. Якщо знахідок 0 — виведи буквально `NO_CONTESTED_DECISIONS`. Інакше — один пункт на знахідку:

```
- **[F{n}] {заголовок в один рядок}** — спричинено: {посилання на журнал правок або рядок чернетки}; суперечить: {§ чернетки + § попереднього артефакту / рядок глосарію / ADR}; пропозиція: {конкретна дія}.
```

Для F5/F6 перелічи кожну прогалину / влучання — по пункту. **Цитування обов'язкове**: кожна знахідка посилається щонайменше на одне місце в чернетці І щонайменше на одне місце в попередньому артефакті. Знахідка без посилань недійсна — краще викинь її, ніж передавай.

### Дисципліна

- НЕ пропонуй доповнень чи зміни скоупу, про які користувач не просив.
- НЕ оскаржуй прийняті рішення, якщо їх не робить неузгодженими записане «Виправити» / «Викинути» / «Винести» чи пізніша секція.
- НЕ більше 7 знахідок — лиши найвпливовіші (пріоритет F4 > F1 > F3 > F2 > F6 > F5).
- Без вступу, без повтору вхідних даних, без підсумку. Лише пункти (або `NO_CONTESTED_DECISIONS`).
- Якщо не можеш прочитати обов'язковий попередній файл — виведи буквально `CRITIC_BLOCKED: <причина>` і зупинись. Не вгадуй.

## Дельта скіла (що підставляє кожен скіл)

- **`{{ARTIFACT_NAME}}`** — напр. "Product Requirements / PRD" або "Software Architecture Document (Arc42, 12 секцій)".
- **`{{UPSTREAM_FILES}}`** — перелік файлів, які критик мусить прочитати (напр. write-prd → `CONTEXT.md`, `idea-brief.md`).
- **Структурний мінімум F5** — конкретний чекліст для цього артефакту (які секції / діаграми / таблиці обов'язкові).
- **Спеціалізація F6** — правила витоку для артефакту. `write-prd`: заборонені токени реалізації в AC (HTTP-методи, URL-шляхи, коди статусу, рядки кодів помилок, конструкції SQL) — перелічити кожне влучання.
